# 时区与时间约定

**铁律：所有应用层时间一律北京时间（UTC+8），ISO 格式带 `+08:00` 后缀。**

服务器 OS 是 UTC，应用层不依赖 OS 时区。

---

## 标准格式

```
2026-05-12T20:48:44+08:00
```

- 形如 ISO 8601
- 精度到秒（不要毫秒，简洁）
- 必带时区后缀 `+08:00`，避免歧义

实现：`pipeline_io.now_iso()`

```python
from datetime import datetime, timezone, timedelta

CN_TZ = timezone(timedelta(hours=8))

def now_iso() -> str:
    return datetime.now(CN_TZ).isoformat(timespec="seconds")

def now_dt() -> datetime:
    return datetime.now(CN_TZ)

def add_days(days: int) -> str:
    return (datetime.now(CN_TZ) + timedelta(days=days)).isoformat(timespec="seconds")

def today_str() -> str:
    return datetime.now(CN_TZ).strftime("%Y-%m-%d")
```

## 用在哪些字段

### 数据库（SQLite）

所有 TEXT 类型的时间字段都是北京时间 ISO：

| 字段 | 用法 |
|------|------|
| `items.created_at` | 入库时间 |
| `items.next_review_at` | 下次复习时间 |
| `items.last_reviewed_at` | 上次复习时间 |
| `tags.created_at` | 首次创建时间 |
| `categories.created_at` | 首次创建时间 |
| `push_history.pushed_at` | 推送时间 |
| `push_history.response_at` | 用户回复时间 |

### md frontmatter

```yaml
created_at: 2026-05-12T14:07:52+08:00
review:
  next: 2026-05-13T14:07:52+08:00
```

### 文件 / 目录名

- md 文件目录：`/www/knowledge/items/YYYY-MM-DD/` — **按北京时区的日期切分**
- Pipeline run_id：`20260512_164842_abc123` — 北京时区时间戳前缀

实现：`pipeline_io.new_run_id()`

```python
def new_run_id() -> str:
    return f"{datetime.now(CN_TZ).strftime('%Y%m%d_%H%M%S')}_{uuid.uuid4().hex[:6]}"
```

## 服务器 OS 时区

```bash
timedatectl
# Time zone: Etc/UTC (UTC, +0000)

date
# Tue May 12 12:49:13 UTC 2026
```

**保持 UTC**，不要 `timedatectl set-timezone Asia/Shanghai`。原因：
1. 服务器是云上备份环境，跨区域恢复时统一 UTC 不出错
2. 量化助手已经依赖 UTC 设定，改了可能坏量化的东西
3. 应用层不依赖 OS 时区，已经统一用 CN_TZ

## Cron 编排（关键）

crontab 走的是 **OS 时区**（也就是 UTC），所以北京时间需要换算：

| 北京时间 | UTC | crontab |
|---------|------|---------|
| 9:00 | 1:00 | `0 1 * * *` |
| 13:00 | 5:00 | `0 5 * * *` |
| 21:00 | 13:00 | `0 13 * * *` |

合并：

```cron
# 北京时间 9:00 / 13:00 / 21:00
0 1,5,13 * * * /usr/local/bin/review-push >> /var/log/review_pusher.log 2>&1
```

⚠️ **改 cron 时间一定要算清 UTC**！

## 同一天去重的判断

`review-push` 同一天不重复推同一条 item：

```sql
NOT EXISTS (
  SELECT 1 FROM push_history p
  WHERE p.item_id = i.id
    AND substr(p.pushed_at, 1, 10) = ?      -- 北京时间今天的 YYYY-MM-DD
)
```

参数：`pipeline_io.today_str()`。

**注意**：`pushed_at` 已经是北京时间 ISO，前 10 个字符就是北京日期。

## 历史遗留数据

数据库里如果有旧的 UTC 时间（在切换到北京时间前写入的），ISO 格式后缀是 `+00:00`：

```
2026-05-12T06:07:52.298418+00:00
```

新写入的统一是 `+08:00`：

```
2026-05-12T14:07:52+08:00
```

两个时间**字面比较**正确（ISO 标准）：
```python
datetime.fromisoformat("2026-05-12T06:07:52+00:00") < datetime.fromisoformat("2026-05-12T14:07:52+08:00")
# True（都是 14:07:52+08, 但前者其实是 14:07 UTC, 后者是 14:07+08 即 06:07 UTC）
```

如果想全部归一为北京时间，可以写迁移脚本（暂未做）。

## 显示给主人时

UI 上**只显示北京时间**，不给"+08:00"后缀：

```
下次推送：2026-05-16T01:30（约 3 天后）
```

实现：`next_at[:16]`（截 ISO 字符串前 16 字符）。

---

## DeepSeek 时间字段

DeepSeek 不需要时间，所以 API 调用层不涉及时区。

但 prompt 里如果传入 `created_at`，会把北京时间字符串原样塞入，LLM 不知道也不关心时区。
